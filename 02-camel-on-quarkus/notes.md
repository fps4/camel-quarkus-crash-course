# What this module is for

- Explain why Red Hat (and many teams on OpenShift) run Camel on Quarkus rather than Spring Boot or
  Karaf, and what it costs.
- Know the moving parts of a Camel Quarkus project well enough to review one: BOMs, extensions,
  `application.properties`, profiles, where routes are discovered, how the HTTP server is shared.
- Use dev mode and Dev Services so the feedback loop is seconds, not minutes.

---

# 1. What Quarkus does differently

Classic Java frameworks do their wiring **at start-up**: scan the classpath, read annotations,
build proxies, read config. Quarkus moves most of that **into the build** (`mvn package`):

| Step | Spring Boot / Karaf / Camel Main | Quarkus |
|---|---|---|
| Classpath scanning, annotation processing | at start | at build (Jandex index) |
| Dependency injection wiring | reflection at start | generated bytecode (ArC, CDI-lite) |
| Camel: component discovery, route model, type converters | at start | mostly at build ("Camel Quarkus core: build-time discovery") |
| Result (JVM mode) | seconds to start, more heap | well under a second for a small app, smaller heap [V for any number you quote] |
| Native image (GraalVM/Mandrel) | possible (Spring AOT) | first-class: `mvn package -Dnative`, ~tens of ms start, small RSS |

Why it matters on OpenShift: many small pods, fast scale-out, rolling deploys, lower memory
requests → more pods per node → lower platform cost. Native also shrinks the attack surface
(no JIT, fewer classes).

What it costs:

- **Reflection and dynamic class loading are restricted in native mode.** Libraries that
  reflect (Jackson on your POJOs, Avro generated classes, JMS `ObjectMessage`) need registration
  (`@RegisterForReflection`) or an extension that does it for you. That is why Camel Quarkus ships
  *extensions*, not plain dependencies.
- **Build-time config is fixed in the artifact.** Some properties can only change by rebuilding
  (marked "fixed at build time" in the docs); runtime ones can be overridden by env vars.
- Native builds are slow (minutes) and need ~4–8 GB RAM; most teams run **JVM mode** in
  production and use native selectively. [V]

# 2. The project

```xml
<dependencyManagement>   <!-- two BOMs, same version -->
  io.quarkus.platform:quarkus-bom:3.40.1
  io.quarkus.platform:quarkus-camel-bom:3.40.1      <!-- aligns Camel Quarkus 3.40.0 / Camel 4.22 -->
</dependencyManagement>
<dependencies>
  org.apache.camel.quarkus:camel-quarkus-kafka      <!-- one extension per Camel component -->
  org.apache.camel.quarkus:camel-quarkus-jms
  io.quarkiverse.artemis:quarkus-artemis-jms        <!-- Artemis client + config + Dev Services -->
  ...
</dependencies>
<plugin>quarkus-maven-plugin: build, generate-code (Avro codegen), dev</plugin>
```

- **Extension = component + build-time glue.** `camel-quarkus-kafka` brings `camel-kafka` plus
  native registration, health checks and Dev Services for Kafka.
- **Routes are discovered automatically.** Any `RouteBuilder` bean (`@ApplicationScoped`) and any
  YAML/XML route under `camel.main.routes-include-pattern` (default `classpath:camel/*`) is loaded.
- **Beans** are CDI beans: `@ApplicationScoped @Named("orderStatusMapper")` → usable in a route as
  `bean("orderStatusMapper", "toEvent")`. A `@Produces` method creates library objects (see
  `IdempotencyConfig`).
- **One HTTP server.** `camel-quarkus-platform-http` serves REST DSL routes on Quarkus' Vert.x
  HTTP server — the same port (8080) as `/q/health` and `/q/metrics`. No embedded Jetty/Undertow
  per component.

## Red Hat build vs upstream

| | Upstream (this lab) | Red Hat build of Apache Camel |
|---|---|---|
| BOM | `io.quarkus.platform:quarkus-camel-bom:3.40.1` | `com.redhat.quarkus.platform:quarkus-camel-bom:<RH version>` from `maven.repository.redhat.com` |
| Versions | Camel 4.22 / Quarkus 3.40 | Camel 4.18 line at time of writing [V] |
| Support | Community | Red Hat support for listed extensions; some are "tech preview" or unsupported |

Ask the platform team which one they use — it decides which Camel features are allowed in
production.

# 3. Configuration

One file, `src/main/resources/application.properties`, for Quarkus, Camel and your own keys:

```properties
camel.component.kafka.brokers=${kafka.bootstrap.servers}     # Camel component option
quarkus.artemis.url=tcp://artemis:61616                       # Quarkus extension option
esb.topic.order-status=orders.order-status.updated.v1         # your own key, used as {{esb.topic.order-status}}
```

- **Profiles:** `%dev.`, `%test.`, `%prod.` prefixes (and `%dev,prod.` for both). `quarkus dev` →
  dev, `@QuarkusTest` → test, the packaged jar → prod. Custom profiles work too
  (`-Dquarkus.profile=kubernetes`).
- **Env vars override everything:** `QUARKUS_ARTEMIS_URL`, `CAMEL_COMPONENT_KAFKA_BROKERS`, or the
  `${ENV_NAME:default}` form used in `esb-lab`. On OpenShift: ConfigMaps and Secrets mapped to env
  vars or mounted files.
- **Placeholders in routes:** `{{esb.topic.order-status}}` is resolved by Camel from the same
  config. Keeps topic and queue names out of code.
- **Secrets:** not in `application.properties`. Use env vars from Secrets, or a vault extension
  (HashiCorp Vault, Azure Key Vault via Camel's vault properties functions). [V]

# 4. Dev mode and Dev Services

`mvn quarkus:dev` (or `quarkus dev`):

- recompiles and restarts **in place** on the next request after a file save (routes, beans,
  config, Avro schemas);
- **Dev UI** at http://localhost:8080/q/dev-ui: Camel routes and their stats, config editor,
  extensions, health;
- press `r` to rerun tests continuously.

**Dev Services:** if an extension needs a server and you did not configure one, Quarkus starts a
container for it (Kafka, Artemis, Postgres, Apicurio Registry, Keycloak, …) via Testcontainers and
wires the URL in. In `esb-lab` the dev profile points at the lab host instead (through the tunnel),
so Dev Services stay off in dev and switch on only in tests (module 06).

# 5. REST DSL on platform-http

```java
restConfiguration().bindingMode(RestBindingMode.json);
rest("/api/v1")
    .post("/order-status")
        .consumes("application/json").produces("application/json")
        .type(OrderStatusRequest.class)           // JSON body -> POJO (Jackson) before the route
        .to("direct:publish-order-status");
```

- **Binding mode `json`**: Camel unmarshals the request into `type(...)` and marshals whatever the
  route leaves in the body (a `Map`, a POJO) back to JSON.
- **Status codes:** set the header `Exchange.HTTP_RESPONSE_CODE` (`CamelHttpResponseCode`).
- **Contract-first** (what a reviewer prefers for partner APIs): write the OpenAPI document
  first, then generate the REST DSL from it (`camel-quarkus-rest-openapi`, or the upstream example
  `openapi-contract-first`). External partner APIs often sit behind an API gateway such as
  3scale; the Camel route is the backend.
- **Alternative:** a Quarkus REST (JAX-RS) resource that calls a Camel route through a
  `ProducerTemplate`. Fine when the API layer is owned by a different team or needs features the
  REST DSL lacks.

# In practice

For an organisation that runs its ESB as Camel routes on Quarkus, with Artemis and Kafka, on
OpenShift with GitOps (ArgoCD):

- Quarkus is the reason the bus apps start fast and scale on OpenShift. Native is optional — ask
  the platform team if they use it, and for which apps.
- Such a setup needs BOM discipline: one platform version across all bus apps, upgraded together
  (an LTS every ~6 months). A good question for the team: **"How do you roll a Camel Quarkus LTS
  upgrade across all routes — one repo or many, and who owns the BOM?"**
- Config by profile + env vars matches GitOps: ArgoCD applies the same image to test/acceptance/prod
  with different ConfigMaps.

# Check yourself

1. *Why Quarkus over Spring Boot for integration?* Faster start, lower memory, native option; same
   Camel API. Cost: build-time constraints, native caveats, a smaller pool of developers who know it.
2. *What is a Camel Quarkus extension, compared with adding `camel-kafka` as a plain dependency?*
   Component + build-time processing (native registration, config mapping, health, Dev Services).
   A plain dependency often works in JVM mode and breaks in native.
3. *How do you override a property in OpenShift without a rebuild?* Env var or mounted config
   file — unless the property is fixed at build time.
4. *Where do REST DSL routes run — embedded Jetty?* No: on Quarkus' Vert.x HTTP server via
   `platform-http`, same port as health and metrics.
